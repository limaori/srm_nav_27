# 哨兵导航 TF 与下位机数据接口

本文整理 MID-360 在底盘或 yaw 云台上安装、底盘是否自旋这四种组合的 TF 解算方法，以及上下位机需要交换的数据。

适用条件：上位机运行 ROS 2、Nav2 和 Point-LIO；导航只控制平移速度 `vx/vy`，底盘角速度 `wz` 完全由下位机控制；现有硬件包括 MID-360、底盘陀螺仪和带编码器的 yaw 电机。这里是设计与接口约定，不代表当前代码已经实现所有接口。

## 1. 结论

**现有传感器足以提供四种情况所需的 TF 观测，不需要为了 TF 再在 yaw 上加陀螺仪。** 前提是 Point-LIO 使用 MID-360 内置 IMU，云台编码器能够提供正确、带时间戳的实际关节角，安装外参已标定。

- 雷达固定在底盘：使用固定安装外参，自旋与否都一样。
- 雷达固定在 yaw：使用编码器关节角计算动态安装外参，自旋与否都一样。
- 底盘真实自旋应保留在 `odom → base_link` 中，无须额外累计“自旋角”再将其剥掉。
- 硬件观测足够不等于任意转速下都能稳定导航，时间同步、LIO 跟踪能力和控制器适配仍需实测。

## 2. 坐标系和位姿计算

导航使用的主链路为：

```text
map → odom → base_link
```

| 坐标系 | 含义 |
|---|---|
| `map` | 已建地图的固定坐标系 |
| `odom` | 本次运行的局部里程计参考系，位姿估计平滑连续，但会漂移 |
| `base_link` | 与实际底盘刚性固定的坐标系，跟随底盘自旋 |

`odom` 可以通过初始化对齐到上电时的底盘位置与朝向，但这取决于实现；不能直接假定 LIO 原始世界系就是初始底盘系。`map` 固定不意味着 `map → odom` 固定：全局定位通常通过更新这条变换修正里程计漂移。

定义 `T(A ← B)` 为将 B 系坐标变换到 A 系的刚体变换。若 LIO 给出雷达位姿：

```text
T(odom ← base_link)
  = T(odom ← lidar) × T(lidar ← base_link, q)
```

其中 `q` 为云台相对底盘的关节角。雷达在底盘上时，第二项是常量；雷达在 yaw 上时，第二项随 `q` 变化。

**先确认 Point-LIO 输出对应哪个机体坐标系。** 若输出的是内置 IMU/body 位姿，应使用 `T(odom ← imu) × T(imu ← base_link, q)`，或先通过固定雷达—IMU 外参转换到雷达系，不能把 IMU 原点直接当成雷达原点。

## 3. 四种组合

| 情况 | 雷达挂点 | 底盘自旋 | 求底盘位姿所需外参 | 下位机必须额外提供的 TF 观测 |
|---|---|---|---|---|
| 1 | 底盘 | 否 | 固定雷达/IMU—底盘外参 | 无 |
| 2 | 底盘 | 是 | 同情况1 | 无 |
| 3 | yaw 云台 | 否 | 根据关节角计算的动态外参 | 云台相对底盘的实际关节角及采样时间 |
| 4 | yaw 云台 | 是 | 同情况3 | 云台相对底盘的实际关节角及采样时间 |

“无”仅指上述 TF 几何解算不依赖下位机额外观测，实际速度和模式反馈仍有价值。

### 3.1 雷达固定在底盘

雷达随底盘一起旋转，LIO 估计的姿态包含底盘自旋，这是正确的真实运动。Nav2 看到底盘 yaw 变化并不是 TF 错误。

即使不自旋，也应应用完整固定外参。只有原点与轴向均重合时，LIO 位姿才可直接当作底盘位姿。旋转时，雷达安装偏移会产生杠杆臂运动，需要用外参换回底盘原点。

### 3.2 雷达固定在 yaw 云台

建议的机械坐标链为：

```text
base_link → yaw_mount → gimbal_yaw → lidar → imu
               固定         ↑          固定     固定
                         关节角 q
```

`yaw_mount` 表示固定在底盘上的关节安装坐标系；`yaw_mount → gimbal_yaw` 是绕已标定关节轴的旋转。

```text
T(base_link ← lidar, q)
  = T(base_link ← yaw_mount)
  × T(yaw_mount ← gimbal_yaw, q)
  × T(gimbal_yaw ← lidar)
```

取逆即可得到求底盘位姿所需的 `T(lidar ← base_link, q)`。这包含旋转轴位置、雷达偏心安装和固定安装角，不能只做 yaw 相减。

无论底盘和云台各自如何转动，编码器测得的都是两者的相对角度，因此情况4不需要再额外分解一个“累计自旋角”。若雷达还会随 pitch 等关节运动，也必须加入对应关节角和外参。

## 4. 三类传感器的分工

| 传感器 | 作用 |
|---|---|
| MID-360 点云和内置 IMU | 供 Point-LIO 估计雷达组件的运动；由雷达驱动直接送上位机 |
| yaw 电机编码器 | 提供云台相对底盘的关节角，解决情况3、4的动态外参 |
| 底盘陀螺仪 | 提供实际底盘角速度，用于运动反馈、辅助状态估计和调试 |

Point-LIO 的常规用法要求雷达与其使用的 IMU 刚性固定。使用 MID-360 内置 IMU 时，雷达装在底盘或 yaw 上均满足这一要求。雷达在云台上时，不应直接用底盘 IMU 替代内置 IMU并继续假定两者外参固定。

### 4.1 需要关节角，不是云台世界 yaw

所需角度是编码器给出的 **yaw 相对底盘的实际关节角**，不是陀螺仪积分得到的“云台相对世界上电零点”的角度。

在平面运动、坐标约定一致的条件下，有：

```text
云台世界 yaw = 底盘世界 yaw + 关节角 + 固定零位偏移
```

只有云台世界 yaw 而没有独立底盘朝向时，不能唯一分离出底盘朝向和关节角。云台不自旋或底盘不自旋的口头描述，也不能替代已知的初始相对角度与运动约束。

云台陀螺仪同样会同时测到底盘运动和云台相对运动。在平面且转轴对齐时：

```text
云台角速度 ≈ 底盘角速度 + 关节角速度
```

两颗陀螺仪相减后积分可以估计关节角变化，但需要已知初始角度，且受零偏和同步误差影响。现有编码器已经直接提供所需观测，无须改用这种积分方案。

## 5. 下位机回传数据

以下字段名是建议的协议语义，不是已实现消息或串口结构体的声明。

| 字段 | 含义与单位 | 要求 |
|---|---|---|
| `timestamp` | 实际采样时间，可换算到 ROS 时间 | 必须；异步采样的不同传感器应各有对应时间 |
| `yaw_joint_angle` | 云台相对底盘的实际关节角，rad | 雷达在 yaw 上时必须 |
| `base_wz` | 底盘陀螺仪测得并转换到底盘系的实际 z 轴角速度，rad/s | 强烈建议；不是 TF 解算的必需输入 |
| `yaw_joint_velocity` | 云台相对底盘的关节角速度，rad/s | 建议，用于插值、有限的短时预测 |
| `spin_active` / `mode` | 是否处于自旋状态及底盘控制模式 | 建议 |
| `valid` / 故障状态 | 编码器、陀螺仪等数据是否有效 | 建议 |
| `base_vx`、`base_vy` | 底盘系实际平移速度估计，m/s | 可选，可由轮速估计，供速度反馈和辅助里程计使用 |

不要求下位机专门回传累计自旋角、云台世界绝对 yaw 或完整底盘世界位姿。实际平移速度也可以在上位机从 LIO 等状态估计中获得；不能将收到的 `vx/vy` 指令当作实测速度。

### 5.1 坐标、零位和单位

- `base_link`：朝电池那条边为 `+x`，左侧为 `+y`，上方为 `+z`。
- 角度和角速度按右手定则取正，从上往下看逆时针为正；统一使用 rad、rad/s，速度使用 m/s。
- 约定云台参考方向与底盘 `+x` 对齐时关节角为零，编码器原始零偏和固定安装角需要标定。
- 若电机有减速机构，上传换算后的输出关节角，不能直接把电机转子角当作云台角。
- 最好提供连续累计关节角。若只传 `[-π, π)` 或单圈角，上位机需正确处理跨圈，避免插值时误认为反向转了一整圈。
- 明确上电、重新校零和计数器复位行为，防止关节角无提示跳变。

### 5.2 时间同步与回传频率

动态外参必须使用 **LIO 位姿对应时刻** 的关节角，而不是收到位姿时最新的一帧角度。下位机时间戳应经过时钟同步或偏移、漂移估计映射到 ROS 时间；仅记录串口接收时刻不能消除传输延迟和抖动。

建议以 **100～200 Hz** 作为角度和角速度回传的起点，再根据最大转速、串口带宽、延迟和允许误差调整。这是工程起点，不是固定最低要求。

例如关节相对转速为 `10 rad/s`，时间错位 `10 ms` 会造成约 `0.1 rad`（约 `5.7°`）角度误差。提高频率不能替代时间同步。上位机应缓存带时间戳的数据并插值；数据过期或无效时进入明确的故障处理流程。

### 5.3 ROS 侧接入建议

- 将关节角转换为 `sensor_msgs/msg/JointState`，填写采样时间、与 URDF 一致的关节名及 `position`，可同时填写 `velocity`。
- 使用 `robot_state_publisher` 根据 URDF 和关节状态发布动态机械 TF。
- 底盘陀螺仪可通过独立反馈消息或 `sensor_msgs/msg/Imu` 发布。若仅有角速度，不应伪造姿态；使用 IMU 消息时按约定标记不可用量并设置合理协方差。
- 求 `odom → base_link` 时按 LIO 位姿时间查询动态外参；关节 TF 缺失时不能用单位阵冒充有效外参。
- 每条 TF 边保持唯一发布者，避免同时发布 `odom → lidar` 和 `base_link → lidar` 导致同一子坐标系有多个父节点。LIO 原始位姿可作为话题输入，由转换节点统一发布底盘 TF。

## 6. 导航只控制 vx/vy 时的要求

本车 `wz` 完全由下位机决定，因此接口应明确上位机 `wz` 不参与底盘角速度控制；不再依赖“与自旋叠加还是被覆盖”的模糊约定。实际 `base_wz` 回传用于反馈，不表示 Nav2 获得了朝向控制权。

### 6.1 保留真实 TF，正确转换平移指令

`base_link` 应跟随真实底盘自旋。若上位机在 `odom` 平面系下给出期望速度，发送给下位机前应按实际底盘朝向旋转到车体系：

```text
[vx_base]   [ cos(ψ)  sin(ψ)] [vx_odom]
[vy_base] = [-sin(ψ)  cos(ψ)] [vy_odom]
```

其中 `ψ` 为底盘在 `odom` 中的 yaw。若控制器已经输出实际底盘系速度，就不应重复旋转。使用虚拟导航系时，应查询该系到实际底盘系的变换完成转换；虚拟系不是 TF 解算所必需的，也不能替代真实 `base_link`。

上述二维旋转假设速度表示同一物理参考点。若不同坐标系的原点不重合，还需考虑旋转产生的杠杆臂速度。

自旋时车体系持续变化：一条保持不变的车体系 `vx/vy` 并不代表保持不变的世界系运动方向。速度转换频率、通信延迟和下位机对指令的保持方式必须配合，才能稳定跟踪路径。

### 6.2 控制器和到达判定

仅丢弃默认 Nav2 控制器输出的 `wz`，不能保证路径跟踪正确。需要：

- 使用适合全向底盘、允许平移与底盘朝向独立的控制策略。
- 取消或替换必须通过主动旋转完成的路径对齐、终点朝向对齐和旋转恢复行为。
- 按任务配置到达判定，避免等待上位机无法控制的目标朝向。
- 对自旋期间的扫掠范围进行碰撞检查；非圆形底盘不能忽略旋转改变的占地范围。

## 7. 联调检查

1. 确认 Point-LIO 订阅 MID-360 内置 IMU，核对输出机体系和雷达—IMU 外参。
2. 标定底盘正方向、关节零位、旋转正方向、关节轴位置和雷达安装偏移。
3. 底盘静止，只转云台：雷达在 yaw 上时，恢复出的底盘位置和朝向应基本保持不变。
4. 固定云台关节角，只让底盘自旋：`base_link` yaw 应真实变化；若绕底盘参考原点旋转，该原点位置应基本不变。
5. 同时转动底盘和云台，检查编码器跨圈、数据时间对齐以及动态外参查询。
6. 自旋中给定固定世界方向的平移目标，检查转换后的 `vx/vy` 是否让底盘沿目标方向运动。
7. 检查关节数据丢失或过期时的处理，以及到达目标后是否仍在等待无法控制的朝向。
