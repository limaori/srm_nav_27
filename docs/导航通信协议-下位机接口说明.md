# SRM 校内赛导航通信协议 —— 下位机接口说明

> **交付对象**：下位机（C 板）固件开发者
> **上游**：小电脑（上位机，ROS 2 导航栈）
> **串口**：下位机 **USART1**，115200 8N1，无流控
> **版本**：与《SRM 校内赛导航通信协议》V1.0.0 一致

本文档描述上位机与下位机之间的**串口通信协议**。凡是标 **【协议规定】** 的是双方必须一致的硬约定；标 **【建议】** 的可以自行取舍；标 **【待确认】** 的表示需要双方联调时实测敲定。

---

## 0. 速览

| 项目 | 值 |
| --- | --- |
| 串口 | 下位机 **USART1**，**115200 baud、8 数据位、无校验、1 停止位、无流控** |
| 上→下 帧长 | 固定 **19 字节** = 5 字节帧头 + 12 字节数据 + 2 字节 CRC16；`data_length` 必须为 **12** |
| 上→下 发送方式 | 固定频率**单帧**发送，推荐 100 Hz；帧间要有空闲间隔 |
| 上→下 内容 | 只有 `vx / vy / wz` 三个 `float32`，**没有** `cmd_id` |
| 下→上 帧长 | **9 + data_length** 字节 = 5 字节帧头 + **2 字节 `cmd_id`** + 数据 + 2 字节 CRC16 |
| 下→上 数据包 | `cmd_id = 0x0001`（比赛状态，11 B）、`cmd_id = 0x000B`（机器人状态，13 B） |
| 字节序 | **所有整数与浮点数一律小端（little-endian）** |
| 控制量 | 协议层不缩放、不限幅；下位机自行换算（见 §3） |

**两个方向不对称**，这是最容易写错的地方：

- 上→下：帧头之后**直接**是数据段，**没有** `cmd_id`。
- 下→上：帧头之后**多一个 2 字节 `cmd_id`**，然后才是数据段。

## 1. 硬件与串口配置

```text
上位机(小电脑)  /dev/ttyACM*  ──USB──>  USB-UART 转接板  ──TTL──>  下位机 USART1
```

- 这是 **USB-UART 转接**，不是 USB CDC 虚拟串口（自瞄赛道才是 CDC）。**波特率必须设置且必须为 115200**，设错的表现是"一个字节都收不到"。
- 【协议规定】下位机侧固定使用 **USART1**，**115200 8N1、无流控**。转接板与板子两端波特率必须一致。
- 【建议】TX/RX 交叉接线，并**务必共地（GND）**；USB-UART 转接板与板子必须共用参考地，否则表现为乱码或完全无数据。

### 1.1 上位机侧配置（仅供参考，下位机无需实现）

上位机参数文件 `src/srm27_nav_protocol/config/srm27_nav_protocol.yaml`：

```yaml
/srm27_nav_protocol:
  ros__parameters:
    device_name: /dev/ttyACM0
    baud_rate: 115200
    flow_control: none
    parity: none
    stop_bits: "1"
    debug_print_hex: false
```

设备与权限（Ubuntu，上位机侧操作）：

```bash
ls -l /dev/serial/by-id/            # 推荐用 by-id 路径, 避免 ttyACM 编号变化
sudo usermod -aG dialout "$USER"    # 加入后需重新登录
stty -F /dev/ttyACM0 -a             # 查看当前串口参数
lsof /dev/ttyACM0                   # 排查串口被占用
```

用 `/dev/serial/by-id/usb-...` 而不是写死 `/dev/ttyACM0`：重新插拔后编号可能变化。

小电脑是共用设备，**每人在自己的用户环境下工作**：创建个人用户后要把该用户加入 `dialout` 组（`sudo usermod -aG dialout 用户名`，之后重新登录），否则打不开 `/dev/ttyACM*`。

## 2. 上位机 → 下位机（速度指令）

### 2.1 帧格式（固定 19 字节）

```text
┌────────┬─────────────┬───────┬────────┬──────────────────┬───────────────┐
│ sof    │ data_length │ seq   │ crc8   │ data (12 bytes)  │ crc16         │
│ 0xA5   │ uint16 LE   │ uint8 │ uint8  │ vx / vy / wz     │ uint16 LE     │
│ 1 B    │ 2 B         │ 1 B   │ 1 B    │ 12 B             │ 2 B           │
└────────┴─────────────┴───────┴────────┴──────────────────┴───────────────┘
偏移 0     1–2           3       4        5–16               17–18
```

| 偏移 | 长度 | 字段 | 类型 | 说明 |
| ---: | ---: | --- | --- | --- |
| 0 | 1 | `sof` | `uint8` | 帧起始字节，固定 `0xA5` |
| 1 | 2 | `data_length` | `uint16` 小端 | 数据段长度，**固定 `12`** |
| 3 | 1 | `seq` | `uint8` | 上位机维护的流水号，每帧自增、自然回绕；**下位机不校验** |
| 4 | 1 | `crc8` | `uint8` | 对偏移 0–3 计算，初值 `0xFF` |
| 5 | 12 | `data` | — | 见 §2.3 |
| 17 | 2 | `crc16` | `uint16` 小端 | 对偏移 0–16（`5 + data_length` 字节）计算，初值 `0xFFFF`；**低字节在前** |

【协议规定】要点：

- 这个方向**没有** `cmd_id` / 命令码字段：帧头 5 字节之后**直接**是数据段，不要额外插字节，也不要有填充。
- `crc16` 覆盖到 `data` 最后一字节为止，**不包含自身**，也不包含任何填充字节。
- **下位机只接受数据段长度为 `12` 的帧**；长度不符的帧整帧丢弃，数据不得写入。（即使 CRC 全对也要丢。）

### 2.2 校验算法

| | CRC8（帧头） | CRC16（整包） |
| --- | --- | --- |
| 生成多项式 | `x⁸ + x⁵ + x⁴ + 1`（按反向多项式 `0x8C` 生成） | `0x1021`（反向形式 `0x8408`） |
| 初值 | `0xFF` | `0xFFFF` |
| 最终异或 | 无 | 无 |
| 方向 | 反射（LSB-first） | 反射（LSB-first） |
| 更新方式 | `crc = T8[crc ^ byte]` | `crc = (crc >> 8) ^ T16[(crc ^ byte) & 0xFF]` |
| **上→下** 覆盖范围 | 偏移 0–3，共 **4** 字节 | 偏移 0–16，共 **17** 字节 |
| **下→上** 覆盖范围 | 偏移 0–3，共 **4** 字节 | 偏移 0–(7+len−1)，共 **7+len** 字节 |

CRC16 等价于标准参数组 **CRC-16/MCRF4XX**。

**【协议规定】自检值**（对 ASCII `"123456789"` 计算）：

```text
CRC8  = 0x0B
CRC16 = 0x6F91
```

这两个值必须对得上，否则查表/位运算实现有错。

**C 参考实现（位运算版，不查表，可直接用于固件）**：

```c
#include <stdint.h>

/* CRC8: poly 反向 0x8C, init 0xFF, 反射, 无最终异或 */
static uint8_t crc8_calc(const uint8_t *p, uint32_t len)
{
  uint8_t crc = 0xFF;
  while (len--) {
    crc ^= *p++;
    for (uint8_t i = 0; i < 8; i++)
      crc = (crc & 0x01) ? (uint8_t)((crc >> 1) ^ 0x8C) : (uint8_t)(crc >> 1);
  }
  return crc;
}

/* CRC16: poly 反向 0x8408 = 0x1021 的反射形式, init 0xFFFF, 反射, 无最终异或 */
static uint16_t crc16_calc(const uint8_t *p, uint32_t len)
{
  uint16_t crc = 0xFFFF;
  while (len--) {
    crc ^= *p++;
    for (uint8_t i = 0; i < 8; i++)
      crc = (crc & 0x0001) ? (uint16_t)((crc >> 1) ^ 0x8408) : (uint16_t)(crc >> 1);
  }
  return crc;
}
```

> 本文档中所有示例帧均已用上面这段代码逐字节验证通过。要追求速度可换成 256 项查表版本（多项式与初值同上，结果必须一致）。

### 2.3 数据段

数据段固定 12 字节，只有三个 `float32`：

| 数据段偏移 | 帧偏移 | 字段 | 类型 | 含义 |
| ---: | ---: | --- | --- | --- |
| 0 | 5 | `vx` | `float32` 小端 | 底盘 x 方向速度指令 |
| 4 | 9 | `vy` | `float32` 小端 | 底盘 y 方向速度指令 |
| 8 | 13 | `wz` | `float32` 小端 | 底盘 z 轴角速度指令 |

```c
#pragma pack(push, 1)
typedef struct {
  float vx;
  float vy;
  float wz;
} RobotCmd_s;   /* 12 字节 */
#pragma pack(pop)
```

【协议规定】下位机接收结构体建议这样写（注意 `data_length` 字段是 2 字节）：

```c
#pragma pack(push, 1)
typedef struct {
  uint8_t  sof;           /* 0xA5 */
  uint16_t data_length;   /* 必须 == 12 */
  uint8_t  seq;           /* 不校验 */
  uint8_t  crc8;          /* 覆盖偏移 0-3 */
  float    vx;
  float    vy;
  float    wz;
  uint16_t crc16;         /* 覆盖偏移 0-16, 低字节在前 */
} navigator_recv_t;       /* sizeof == 19 */
#pragma pack(pop)
```

接收侧长度校验：`check_len = sizeof(navigator_recv_t) - 6 = 12`，即 `data_length` 字段必须等于 12。

## 3. 量纲、缩放与坐标系

### 3.1 协议层不做任何换算

【协议规定】协议层不缩放、不限幅，传的就是 `float` 原始值。上位机输出的是**与底盘速度成正比的速度指令**，不是真实速度（不是 m/s）。

上位机（`geometry_msgs/Twist`）是把 `linear.x / linear.y / angular.z` 直接写进 `vx / vy / wz`，沿用 Nav2 输出的数值量级；真正的换算在下位机侧完成，比例见 §3.3。

### 3.2 下位机侧怎么用这三个数

上位机发出的 `vx / vy / wz` 不直接等于底盘的三轴速度，下位机内部有一套换算。可以当协议约定用的有两条：

| 上位机字段 | 底盘实际作用 |
| --- | --- |
| `vx` | 进底盘的 **y 方向** |
| `vy` | **取负**后进底盘的 **x 方向** |
| `wz` | **被忽略**，当前不产生转向 |

也就是存在 **90° 轴向交叉**：上位机的 `+x` 不对应车的正前方，而是对应车的**侧向**。

**【待确认】** 因为存在轴向交叉，上位机侧的正方向定义需要**做一次逐轴实测确认，不要靠推断**。联调时按 §7 的逐轴测试流程敲定，并把结论回写到本文档。

【建议】如果 `wz` 后续要启用（例如哨兵自转），必须与上位机同步修改本文档，并明确：

- 旋转方向的正负定义（右手法则绕 z 轴：`+wz` 为逆时针 / 向左转）；
- 是否与平移叠加，以及叠加时的优先级。

### 3.3 量级参考

下位机速度环的参考值与上位机数值之间大约是 **10000 : 1** 的比例。作为对比，遥控器手动模式下满杆约为 `39600`。所以：

- 上位机 `vx = 1.0` 约等于**四分之一杆**，对哨兵来说已经是相当大的速度指令；
- **起步建议 `vx/vy ≤ 0.2`**，确认方向正确后再逐步放大；
- 【协议规定】协议层不做限幅，**限幅是上位机的责任**（下位机可以再加一层兜底限幅，但不要依赖上位机）。

## 4. 下位机 → 上位机（反馈）

这个方向与上→下**不同**，多一个 2 字节的 `cmd_id`。

### 4.1 帧格式（9 + data_length 字节）

```text
┌────────┬─────────────┬───────┬────────┬──────────┬───────────────┬───────────────┐
│ sof    │ data_length │ seq   │ crc8   │ cmd_id   │ data          │ crc16         │
│ 0xA5   │ uint16 LE   │ uint8 │ uint8  │ uint16 LE│ data_length B │ uint16 LE     │
│ 1 B    │ 2 B         │ 1 B   │ 1 B    │ 2 B      │ 变长           │ 2 B           │
└────────┴─────────────┴───────┴────────┴──────────┴───────────────┴───────────────┘
偏移 0     1–2           3       4        5–6        7…              末 2 字节
```

【协议规定】：

- `crc8`：对偏移 0–3 计算，初值 `0xFF`（与上→下相同）。
- `crc16`：对偏移 0 到 `7 + data_length - 1` 计算，初值 `0xFFFF`，低字节在前。**包含 `cmd_id`**。
- 总帧长 = `5 + 2 + data_length + 2 = 9 + data_length`。
- `cmd_id` 为 2 字节小端，位于偏移 5–6。
- 每个包各自独立成帧，**不要把多个包拼成一条流连发**。

### 4.2 数据包定义

下位机当前发送两个数据包：

| `cmd_id` | 名称 | `data_length` | 总帧长 |
| --- | --- | ---: | ---: |
| `0x0001` | 比赛状态 | `11` | 20 B |
| `0x000B` | 机器人状态 | `13` | 22 B |

**`cmd_id = 0x0001`，数据段 11 字节**（紧凑布局，无填充）：

| 数据段偏移 | 长度 | 字段 | 类型 | 说明 |
| ---: | ---: | --- | --- | --- |
| 0 | 1 | `game_type` : 4 / `game_progress` : 4 | 两个 4 位域 | **低位 4 位**是比赛类型，**高位 4 位**是当前阶段 |
| 1 | 2 | `stage_remain_time` | `uint16` LE | 当前阶段剩余秒数 |
| 3 | 8 | `sync_time_stamp` | `uint64` LE | 裁判系统 NTP 时间戳 |

```c
#pragma pack(push, 1)
typedef struct {
  uint8_t  game_type     : 4;   /* 低位 4 位 */
  uint8_t  game_progress : 4;   /* 高位 4 位 */
  uint16_t stage_remain_time;
  uint64_t sync_time_stamp;
} game_status_t;                /* 11 字节 */
#pragma pack(pop)
```

**`cmd_id = 0x000B`，数据段 13 字节**：

| 数据段偏移 | 长度 | 字段 | 类型 |
| ---: | ---: | --- | --- |
| 0 | 1 | `robot_id` | `uint8` |
| 1 | 1 | `robot_level` | `uint8` |
| 2 | 2 | `current_HP` | `uint16` LE |
| 4 | 2 | `maximum_HP` | `uint16` LE |
| 6 | 2 | `shooter_barrel_cooling_value` | `uint16` LE |
| 8 | 2 | `shooter_barrel_heat_limit` | `uint16` LE |
| 10 | 2 | `chassis_power_limit` | `uint16` LE |
| 12 | 1 | 电源输出标志位 | 3 个 bit：bit0 gimbal / bit1 chassis / bit2 shooter（1 = 24V 输出） |

```c
#pragma pack(push, 1)
typedef struct {
  uint8_t  robot_id;                          /* 本机器人 ID */
  uint8_t  robot_level;                       /* 机器人等级 */
  uint16_t current_HP;                        /* 当前血量 */
  uint16_t maximum_HP;                        /* 血量上限 */
  uint16_t shooter_barrel_cooling_value;      /* 射击热量每秒冷却值 */
  uint16_t shooter_barrel_heat_limit;         /* 射击热量上限 */
  uint16_t chassis_power_limit;               /* 底盘功率上限 */
  uint8_t  power_management_gimbal_output  : 1;  /* bit0 */
  uint8_t  power_management_chassis_output : 1;  /* bit1 */
  uint8_t  power_management_shooter_output : 1;  /* bit2 */
} robot_status_t;                               /* 13 字节 */
#pragma pack(pop)
```

### 4.3 反馈包示例帧

`cmd_id = 0x0001`，`game_type/game_progress = 0xAA`，`stage_remain_time = 300`，`sync_time_stamp = 0x1122334455667788`，`seq = 1`：

```text
A5 0B 00 01 5C 01 00 AA 2C 01 88 77 66 55 44 33 22 11 EF 74
│           │  └──┬──┘ └────────────┬────────────┘ └──┬──┘
│           │     │                 │                  └─ crc16 = 0x74EF (低字节 EF 在前)
│           │     │                 └─ data (11 B): 0xAA, 300, timestamp
│           │     └─ cmd_id = 0x0001 (低字节 01 在前)
│           └─ crc8 = 0x5C
└─ sof, data_length = 0x000B = 11, seq = 01
```

逐字段核对：

```text
A5           sof
0B 00        data_length = 11
01           seq
5C           crc8  = 0x5C        (覆盖 A5 0B 00 01)
01 00        cmd_id = 0x0001
AA           game_type=0xA(10), game_progress=0xA(10)
2C 01        stage_remain_time = 300
88 77 66 55 44 33 22 11   sync_time_stamp = 0x1122334455667788
EF 74        crc16 = 0x74EF      (覆盖前 18 字节)
```

## 5. 参考向量与自检

### 5.1 上→下 参考帧（`seq = 0x01`）

可直接核对自己的打包函数：

| 指令 | 19 字节完整帧（十六进制） |
| --- | --- |
| `vx=1, vy=0, wz=0` | `A5 0C 00 01 26 00 00 80 3F 00 00 00 00 00 00 00 00 6B A3` |
| `vx=0, vy=0, wz=0`（停车帧） | `A5 0C 00 01 26 00 00 00 00 00 00 00 00 00 00 00 00 18 9F` |
| `vx=1, vy=-1, wz=3` | `A5 0C 00 01 26 00 00 80 3F 00 00 80 BF 00 00 40 40 D3 96` |

第一帧逐字段核对：

```text
A5           sof
0C 00        data_length = 12
01           seq
26           crc8  = 0x26        (覆盖 A5 0C 00 01)
00 00 80 3F  vx = 1.0f
00 00 00 00  vy = 0.0f
00 00 00 00  wz = 0.0f
6B A3        crc16 = 0xA36B      (覆盖前 17 字节, 低字节在前)
```

### 5.2 自检清单

实现完成后请依次确认：

1. `crc8_calc("123456789", 9) == 0x0B`
2. `crc16_calc("123456789", 9) == 0x6F91`
3. 用 `vx=1, vy=0, wz=0, seq=1` 组帧，得到上面第一条 19 字节序列
4. 用 §4.3 的参数组 0x0001 反馈帧，得到上面那条 20 字节序列
5. 收到 `data_length != 12` 的上→下帧时，确认整帧被丢弃且不写入控制量

## 6. 下位机需要实现的行为清单

### 6.1 接收（上位机 → 下位机）

| # | 行为 | 级别 |
| --- | --- | --- |
| 1 | 按 `SOF = 0xA5` 查找帧起点 | 【协议规定】 |
| 2 | 校验 `crc8`（偏移 0–3）；失败则丢弃 1 字节后**重新同步**（滑动窗口），不要清空整个缓冲 | 【协议规定】 |
| 3 | 严格校验 `data_length == 12`；不符则**整帧丢弃**，数据不得写入 | 【协议规定】 |
| 4 | 收满 19 字节后校验 `crc16`（偏移 0–16）；失败同样丢 1 字节重新同步 | 【协议规定】 |
| 5 | `seq` 不校验（可以记录用于统计丢帧，但不作为有效性条件） | 【协议规定】 |
| 6 | 采用最后一次**有效**指令，并**持续保持**该速度 —— 协议没有超时保护 | 【协议规定】 |
| 7 | 建议加看门狗：超过 **500 ms** 未收到有效帧 → 速度归零 | 【建议】 |

> **安全提示**：第 6 条意味着**上位机崩溃或拔线时，底盘会按最后一帧的速度一直跑下去**。第 7 条的看门狗能显著降低这个风险，建议实现；若实现，请把超时时间写回本文档。

### 6.2 发送（下位机 → 上位机）

| # | 行为 | 级别 |
| --- | --- | --- |
| 1 | 按 `9 + data_length` 组帧，`cmd_id` 在偏移 5–6，小端 | 【协议规定】 |
| 2 | `crc16` 必须**包含 `cmd_id`**（覆盖偏移 0 到 `7+len−1`） | 【协议规定】 |
| 3 | 每个包独立成帧，**不要**把多个包背靠背拼成一条流 | 【协议规定】 |
| 4 | 发送频率 ≥ 20–50 Hz，与速度指令接收解耦 | 【建议】 |
| 5 | 未接裁判系统时也要能正常发 0x0001 / 0x000B（可用 0 值填充），便于上位机判断链路是否通 | 【建议】 |

### 6.3 固件侧排查点

如果一切帧都正确但底盘不动，检查：

- `navigator_init(&huart1)` 是否**被注释掉**了 —— 接收回调未注册时，无论帧多正确都不会动。历史版本 `control-2026 a6e1638` 在 `UserApp/robot/sentry_omni_chassis/robot.c:490` 就有这个问题。
- 接收长度校验用的 `check_len` 是否等于 12。
- USART1 的接收是否用了 DMA + 空闲中断，以及是否与其它外设冲突。

## 7. 联调流程与已知事项

### 7.1 逐步联调流程

先不要直接上 ROS 导航栈。按下面顺序排查，每步只验证一件事：

1. **上位机 → 下位机方向**：用小电脑直发 §5.1 的三条参考帧，确认下位机解析正确（可用调试串口/灯/变量观察）。
2. **逐轴确认方向**（敲定 §3.2 的待确认项）：分别只发 `vx=+0.1`、`vx=-0.1`、`vy=+0.1`、`vy=-0.1`，各持续 1 秒，记录车体实际运动方向。**四轴全部实测**，形成结论后回写本文档。
3. **下位机 → 上位机方向**：确认上位机能收到 0x0001 / 0x000B，且解析出来的字段与下位机实际状态一致。
4. **安全语义**：确认上位机停发 / 拔线时底盘的行为符合预期（是否按第 6.1.7 条看门狗归零）。
5. 以上全通之后，再接入 ROS 导航栈整机联调。

### 7.2 上位机实现状态：已与本文档一致

上位机 ROS 节点 `src/srm27_nav_protocol` 发出的上→下帧是**标准 19 字节帧**，与本文档 §2.1 完全一致：

- 数据段 12 字节，`data_length = 12`，整帧 19 字节；
- `packet_typedef.hpp` 中有 `static_assert(sizeof(SendRobotCmdData) == 19)`，**往数据段里加字段会在编译期直接失败**，不会静默发出下位机不认的帧。

节点侧的协议行为（对应 §6）：

| 项 | 实现 |
| --- | --- |
| 发送频率 | 100 Hz 定频（`send_rate_hz`，上限 200 Hz 保护 §6.2） |
| 帧间空闲 | 周期以"上一帧发完"为基准计算，被抢占时只顺延、不补发，不会背靠背 |
| 启动即发 | 未收到 `cmd_vel` 时持续发零速帧（§6.3） |
| 看门狗 | `cmd_vel` 超过 500 ms 未更新则控制量归零（`cmd_timeout_sec`，§6.3） |
| NaN/Inf | 回调处拦掉并按零速处理（§6.4） |
| 限幅 | `max_vx/max_vy/max_wz`，默认 0.5 / 0.5 / 1.0，即 nav2 omni 控制器自身的输出上限（§6.5） |
| 退出补零速 | 正常结束 / Ctrl-C / 异常均在关串口前连发 10 帧零速（§6.3） |

已实测验证（`socat` 虚拟串口抓取节点实际发出的字节）：连续 828 帧**全部**通过 `data_length==12` + CRC8 + CRC16 严格校验，实测 99.3 Hz / 间隔 10.08 ms，正常指令原样透传、超限指令被截断、看门狗 500 ms 归零、SIGINT 后补发 10 个零速帧。节点与测试工具的打包结果**逐字节一致**，且都等于 §5 的三条参考向量。

**【重要】若下位机收到 `data_length = 13` / 整帧 20 字节的帧**：那是**旧版本上位机**（曾在数据段多发一个 `is_recovering` 字节）。该字段现已删除，如仍观察到，说明跑的是未更新的可执行文件，重新编译 `srm27_nav_protocol` 即可。下位机侧**不需要**为它做任何兼容。

### 7.3 联调工具

仓库内提供了一个直发标准 19 字节帧的工具，可用于 §7.1 的第 1、2 步（把 ROS 导航栈整个排除在外）：


## 8. 上位机发送要求

这一节是上位机侧的约束，列出以便双方理解链路行为。

1. **固定频率单帧发送。** 推荐 100 Hz（19 字节在 115200 baud 下约 1.65 ms，留出的空闲足够）。
2. **不要背靠背连发。** 每帧之间要有空闲间隔；把多个帧连成一条流会让下位机错位丢帧。
3. **持续发送是安全前提。** 协议没有超时保护：下位机一直使用最后一次收到的有效指令。因此：进程启动即开始发送（哪怕只发零速帧）；退出、异常、Ctrl-C、串口断线都要补发零速度帧。
4. **不要发送 `NaN` / `Inf`。** 解算异常时先做 `isfinite` 检查，回退到零速帧。
5. **自己做限幅。** 把 `vx/vy/wz` 限制在安全范围内再发送；从保守值起步（如 `vx/vy ≤ 0.2`），确认符号与轴向正确后再逐步放大。
6. **发送线程里不要做重活。** 日志、文件写入、网络请求都会让定频心跳抖动；发送线程只做打包 + `write`。
