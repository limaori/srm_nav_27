# 2026-11-27 map→odom 累计修正预算（换图后"跳着转"的止血）

## 现象

- 版本 `61b03a4` + 先验图 `219_1121`：云台怎么转都不飘。
- 换成 `227to219_1125`：一开始不飘，车往前跑几米后 **`map→odom` 跳着转**，定位崩溃
  （状态机上是 `SUSPECT` / `LOST` → `recovered via Scan Context + scan-to-map`）。

## 根因：两个独立缺陷叠在一起

### 1. 这张图的全局描述子已经没有判别力（选图问题）

用 `debug_tools/check_sc_separability.py` 直接解析 bundle 里落盘的
`sc_descriptors.bin`（`0x53435859`，每帧 3 个变体、30×90），按
`src/scan_context/descriptor.cpp::descriptorDistance` 同口径计算：

| 量 | 227to219_1125 | 219_1121 |
| --- | ---: | ---: |
| 正确位置 d_true 中位 | 0.059 | 0.000 |
| 错误位置（≥20 m）d_false 中位 | **0.000** | 0.000 |
| d_false < `distance_threshold=0.8` | **31/31** | 44/44 |
| 错解排序优于正解 | **90%** | 86% |
| 帧数 / 覆盖 | 1960 / 51×82 m | 48 / 8.7×11.6 m |

阈值形同虚设，检索等于随机挑候选。**旧图同样不可分**，但它最远的"别处"只有
8~10 m（选错也错不出那个小房间）；新图两段同构走廊相距 20~50 m，一次选错就是
几十米 + 180°。

建包侧的直接成因：`build_zloc_map_bundle.sh` 没有透传 `--max-distance`，
工具默认 80 m，于是每一帧"模拟扫描"其实是整张图（实测每帧 40k 点 = 全图），
近处与远处结构被同等权重地编进描述子。

试过把范围裁到 25/30 m 重建（`maxr25 r20 s60` / `maxr30 r30 s90`），d_false 仍是
0.000 —— 这张图本身就是"Y 形直走廊"，平移 20~50 m 或转 180° 后几何自相似，
**不是调参能修的，必须动图**。

### 2. 逐次幅度上限挡不住"累计"（代码问题，本次已修）

`tracking.max_rotation_correction_deg=15` + `correction_period=0.5 s` 等价于允许
**30°/s** 的稳态旋转（180° 只要 6 s）；恢复路径 20°/次，实测 2.8 s 内提交过 3 次。

根因是闸门比较的是"本次测量 vs **当前预测**"，而预测是拿当前 `map→odom` 算的：

```cpp
// observation.cpp
work.predicted_map_pose = poses_.transform() * work.runtime.odom_pose;
// tracking_matcher.cpp
correction = predicted.inverse() * measured;
```

上一次已经吃进去的错误变成了下一次的基准 —— 典型的积分饱和。把 15 改成 5 只是把
转速从 30°/s 降到 10°/s，方向不变。

## 改动：`correction_anchor` 累计预算

新增 `include/backend/correction_anchor.hpp`（纯逻辑，无 ROS/PCL 依赖）：

- 记一个 `map→odom` 锚点 A，候选提交前检查
  `|yaw(A⁻¹·candidate)| ≤ max_rotation_deg` 且 `|xy| ≤ max_translation`；
- A **不随错误移动**：只有"安静"的提交（本次实际修正量 ≤ `reseat_*`）且**连续**
  `reseat_quiet_frames` 帧之后才前移 —— 这一步同时掐掉"跳一次 → 安静一帧 → 再跳一次"
  的锯齿；
- 冷启动（`initialize()` 之后、没有可信位姿）不设限，首次提交直接落锚；
- 前端换代（`reframeOdometry`）时锚点按 `anchor · old_from_new` 同步换算，避免换代后
  第一个候选就被误杀；
- 人工 `/backend_node/relocalize` 提交成功后强制重落锚（"我知道车在哪"的显式声明）。

接线：`PoseOutput` 持有锚点；跟踪路径在 `collectGlobalInnovationsLocked` 里越界即
当作 **冲突证据**（走既有 `conflict → SUSPECT` 冻结路径，而不是把 TF 转过去）；
恢复路径在 `commit(RecoveryWork, RecoveryResult)` 里与单次预算并联。

配置（`backend.yaml` 默认 / `srm27_localization_real.yaml` 实车）：

```yaml
correction_anchor:
  enabled: true
  max_rotation_deg: 8.0      # 实车 8°，默认 10°
  max_translation: 0.8       # 实车 0.8 m，默认 1.0
  reseat_rotation_deg: 1.0
  reseat_translation: 0.15
  reseat_quiet_frames: 5
```

启动时会打印生效值，现场第一眼就能确认：

```
[backend] map->odom cumulative correction anchor: enabled=true, max_rotation_deg=8,
          max_translation=0.8m, reseat=1deg/0.15m x5 frames
```

> ⚠ `max_*_correction: 0` 在本仓库的语义是**不检查（不限幅）**，不是"禁止修正"
> （`config.hpp` 里是 `> 0.0 &&` 判断）。关掉 yaw 修正不能填 0。

## 验证

- `backend_correction_anchor_test`（12 例）：冷启动、连续跳变撞线、平移/旋转独立轴、
  缓慢真实漂移不被误杀、锯齿不被追认、安静够数后重落锚、人工重落锚、`clear()`、
  非有限输入。
- `backend_localization_test.CumulativeAnchorStopsRepeatedSmallRotations`（端到端）：
  每步注入 1.5°（能过 NIS 创新门，又高于 1° 的"安静"阈值），第 6 步累计 9° 被拒：

  ```
  conflict 1/1000: prior scan-to-map over cumulative correction anchor: delta_r_deg=9 (limit 8)
  conflict 3/1000: ... delta_r_deg=12 (limit 8)
  ```
  实测 `map→odom` 停在前 5 步累计的 ~7.5°，不设闸时会到 15°。
  （注：步长不能取 5° —— 那会先被 NIS 创新门拒掉，走不到累计闸。）
- 全量非 pytest 测试 13/13 通过；`ros2 launch ... prior_map:=219_1121` 冒烟通过，
  无未知参数错误，启动日志确认 8° 生效。

## 追加（2026-11-27 下午）：冻结的真正触发条件 = 云台快速自转

### 现场

`real_zloc_1127_152802`（117 s）与 `real_zloc_1127_154344`（87 s）两次实车：
前半段 NORMAL，云台开始自转后先验观测整片冲突，37.8 s / 之后升级 SUSPECT → 冻结。
冻结期间 `map→odom` 跨度 **2347°**、`odom→body` **2347°** —— **完全 1:1**，是冻结投影
`T_map_odom = T_map_sensor_frozen · T_odom_sensor⁻¹` 的必然结果；
`map→body` 全程只在 0.4×0.7 m 盒子里，**没有任何错误位姿被提交**。
闸门日志实测挡下了 180°/148° 的恢复提交（`over correction budget`）。

### 第一次尝试（无效）：收窄累积窗口

`tracking/recovery.source.max_rotation_deg: 0 → 20`（0 = 不限制）。
生效确认：冲突时的 `source_span` 从 0.40 s 降到 **0.10 s**（`source_frames=2/5`），
**但 NIS 依旧 88~326**。→ 不是点云被累积糊住，假设被数据否掉。

### 真正特征：误差几乎全在平移

一条典型冲突：

```
delta_t=0.3856 m, delta_r_deg=0.549, NIS=167.9/6
```

平移动 0.2~0.5 m 而旋转只差 0.3°，说明**预测位姿在自转时本身对不齐**，
而不是配准解偏。怀疑对象：`pose_body_offset_xyz: [0.009, -0.226, -0.130]`
只加在发布的位姿上（`pose_body_offset_apply_to_cloud: False`），点云没加；
云台一转，这个车体系常量在世界系里的方向就变 → 位姿与点云自相矛盾。
（相关背景：`docs/records/2026-11-24-云台点云平移绕圈(ai).md`）

### 本次实现：自转时**跳过**先验观测

`tracking.max_body_angular_rate_deg: 60`（实车 profile；默认 0 = 关闭）。
超过阈值时该周期不产生先验观测：

- 走 `prior_input.configured = false` → 无 UWB 时 `captureTracking` 直接返回空，
  **不产生观测、不计冲突、不推进状态机**；
- 状态保持 NORMAL，定位按 odom 递推，转速降下来后自动恢复纠偏。

⚠️ 实现要点：角速度必须读 `frames_.odometry()`（保留 ≥2 s）而不是
`frames_.history()` —— 后者按 `max(tracking.source.max_frames, recovery.source.max_frames)`
裁剪，配置成 1 时只剩一帧，取不到"上两帧"，闸门会**静默失效**（第一版就栽在这）。

启动日志会打印生效值，现场一眼可查：

```
[backend] prior scan-to-map body-rate gate: 60 deg/s (skip observation)
```

验证：`backend_localization_test.FastBodySpinSkipsPriorObservationsInsteadOfConflicting`
（300°/s 自转 2 s，断言全程 NORMAL 且 `map→odom` 不变）+ 全量 13/13 通过。

### 仍未排除

`pose_body_offset_xyz` 的位姿/点云不一致。若加了自转闸仍偶发冲突，
下一步做 A/B：把 `pose_body_offset_xyz` 置 `[0,0,0]` 再测一轮。

## 追加（2026-11-27 16:15 bag）：闸门两个洞 + offset 位姿/点云不一致

### 数据（`real_zloc_1127_161502`，128 s）

- 0–34 s 云台不动，NORMAL，`map→odom ≈ -7.9°` 不动；
- 34.2 s 起云台 ±180° 来回扫、约 200°/s；
- **34–91 s `map→odom` 仍是 -7.8~-8.1°，`map→base_link` 只在 61–78° 小摆**
  —— NORMAL 下地图没转；
- 90.7 s conflict → 91.3 s SUSPECT(frozen) → LOST；之后 `map→odom` 跟着云台反向转
  （-769°、-1817°…），`map→base_link` 摆 2717°。**"地图跟着转"是冻结后的投影**，
  不是校正把地图转走。

> `diag_map_odom_spin.py` 默认 `body_frame=gimbal_yaw`，把"云台真转"误判成"车被转走"
> （结论"校正被吃进地图系"）。判据应改用 `base_link`，或只在本包冻结时段看平移。

### 为什么 200°/s 自转时闸门没拦住

自转 57 s 内本应 0 次观测，实际 25 次（9 accepted + 16 conflict，约 22% 周期被放行）：

1. 旧实现只看 `t-0.1 s` 的**净转角**。云台反向时正反转抵消、净转角≈0；
   实测 12.5% 的 0.1 s 窗口 < 60°/s。
2. `poseAt(t-0.1, 0.05)`：前端帧 9.3 Hz（间隔 0.107 s），最近样本最大差 0.054 s > 0.05，
   约 13% 返回 nullopt → 闸门静默失效。
3. 冲突 `delta_t=0.2~0.47 m`、`delta_r=0.2~1.4°`，量级正好是
   `pose_body_offset_xyz`（|0.26 m|）在云台转动时被乘进 backend 位姿、却没进点云
   （`zlio_bridge._backend_pose_provider` vs `adapter.py:279 adapted.cloud = message.cloud`）。

### 本次改动（P0+P1）

- 配置 A/B：`pose_body_offset_xyz: [0.009,-0.226,-0.130] → [0,0,0]`
  （nav + mapping 两份，回归测试钉住同值）。
- `Localization::bodyRateGateLocked()`：0.5 s 窗口逐段 `Σ|Δθ|`（路径长度）+ 0.2 s
  采样容差 + 0.5 s 迟滞；tracking 与 recovery 共用（INITIALIZING 与人工 relocalize 不闸）。
- 测试：新增 `BodySpinGateUsesPathLengthNotNetRotation`（反向 ±20°，净转角≈0、
  路径长度 ~400°/s）；`backend_localization_test` 全量 40/40 通过。

### 下一步（P2，待确认）

冻结时不要冻 `T_map_sensor`（云台一转 `map→odom` 必然反向转），改成冻 `T_map_odom`
= 只用前端里程计递推；后端继续在后台尝试恢复，成功后提交并回到 NORMAL+先验。

`recovery.automatic_when_lost=false` 时 LOST 不自动重试；要"一直试"可打开，但先验图
（227to219_1125）描述子不可分，全局恢复有传送风险，建议保持人工 relocalize 或只放宽到
SUSPECT。

### 下位机云台 yaw

bag 里 `/joint_states` 的 `gimbal_yaw_joint` 只摆 6.3°，而 `/gimbal_joint_angle`
是 ±180° —— **不能用 joint_states 当真实云台角**。下位机回传可用时优先用它：
1) gate 直接读 `|Δgimbal|/Δt`（比从 lidar odom 猜更稳，反向也不怕）；
2) 更彻底：用它把 `T_odom_lidar` 换成 `T_odom_base`、把局部点云转到 base 系，
   backend 的先验匹配就完全不受云台转影响（需要 C++ 或 bridge 承担每帧点云变换）。

## 追加（2026-11-27 16:52 bag）：P1 生效，但 offset 清零把圆周晃动带回来了

### P1 结果（`real_zloc_1127_165237`，116 s）

- 云台全程 ~193°/s 来回扫（±180°，6625°），`map→odom` 跨度 **0.2°**；
- `tf_frozen=true` **0%**、`pose_trusted=false` **0%**、状态全程 **NORMAL**；
- backend 日志：**accepted 74 / conflicted 0 / 无 SUSPECT/LOST**。

自转期间仍有 29 次观测被接受，但不是闸门漏：`/gimbal_joint_angle` 统计显示
\|rate\|<60°/s 的时间占 **27%**（0–10.6 s、12.4–19.0 s、102.7–115.8 s 几段停顿），
这些观测都落在停顿里，且 P0 的位姿/点云自洽，所以 NIS 正常。

> `analysis.txt` 这次写"map→odom 锁存：没有任何全局校正"是误判：整段几乎都在自转，
> 闸门按设计跳过观测，map→odom 平直正是**成功判据**，不是 `--zloc-prior-once`。
> 工具的判据要把"自转窗口内 map→odom 平直"单独判为 PASS。

### 圆周晃动回来了

P0 把 offset 清零后，ZLIO 在云台自转下的原始平移偏置重新暴露：

| 量（TF 拟合 vs 云台角） | 半径 |
| --- | ---: |
| `odom→gimbal_yaw` 平移 | **0.271 / 0.261 m** |
| `map→base_link` 平移 | **0.270 / 0.259 m** |
| `pose_body_offset_xyz`（被清零的值） | 0.261 m |

离线复算：把 bag 的原始 `/lidar_odometry` 右乘 `[0.009,-0.226,-0.130]`，
`odom→gimbal_yaw` 的平移圆半径从 **0.27 m 降到 0.024 m**（残差不变）。
所以"定位圆周晃动"就是被清零的那个 offset，量级完全对得上。

### 修法：offset 只走输出链，不进 backend 输入

- `zlio_bridge._backend_pose_provider()`：**不再**乘 `pose_body_offset`，backend 拿到
  原始 `T_odom_lidar`（与适配层发的原始局部点云同系）；
- `zlio_bridge._publish()`：新增 `backend_pose=raw`，`lidar_odometry`/TF 仍用
  `pose_pub = pose * offset`；
- 配置恢复 `pose_body_offset_xyz: [0.009,-0.226,-0.130]`（nav + mapping 同值）。

链路：backend 的 `map→odom` 用原始位姿算 → `odom→gimbal_yaw`（经
`sensor_scan_generation` 用 `/lidar_odometry` 的 offset 位姿）→ `map→base`
= `T_map_sensor_raw · O · 外参`，即修正后的车体位姿。既不改 backend 因子图，
也把发布位姿的圆压到 ~2.4 cm。
