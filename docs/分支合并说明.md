# 分支合并说明

## 目标：保留开发提交，并生成一个合并提交

开发分支可以有多个提交，合入 `main` 时保留这些提交，并额外生成一个 `Merge branch '...'` 合并提交。在 Git 日志图中，可以看到分支分叉和汇合的关系。

统一使用 **`git merge --no-ff`（禁止快进合并）** 实现这个效果。

例如，合并前：

```text
main：A
       \
开发：  B ── C ── D
```

合并后：

```text
main：A ─────────── M
       \           /
开发：  B ── C ── D
```

`M` 是新生成的合并提交，包含两个父提交：合并前的 `main` 提交 `A` 和开发分支末尾的提交 `D`。`B`、`C`、`D` 也会进入 `main` 的历史。

这里的“一个合并提交”并不表示整个历史只增加一个提交。若希望隐藏开发过程、只留下一个汇总提交，应使用 squash；本文采用保留完整开发历史的方式。

## 已有案例：仿真重定位分支

`pb2025_sentry_ws` 中的 `b107dc7` 提交：

```text
Merge branch 'feat/仿真重定位测试'
```

它有两个父提交：

- `ee659b7`：合并前的 `main`。
- `0ca7d96`：`feat/仿真重定位测试` 的末尾提交。

这是一次非快进合并，本地 reflog 记录使用了 `ort` 合并策略。当时两个分支已经分叉，普通 `git merge` 也会生成合并提交；仅凭这些记录不能确定当时是否显式使用了 `--no-ff`。

如果 `main` 没有新增提交、只是落后于开发分支，普通合并通常会直接移动 `main` 指针，也就是快进（Fast-forward），不会生成合并提交。显式指定 `--no-ff` 可以让这种情况也生成合并节点。若来源分支已经完全合入，则不会再次生成合并提交。

## 合并前必做检查与合并后验证

这一节和 IDE 无关，无论用 CLion 界面还是内置终端都要做。下面的「CLion」和「终端」两节只讲怎么触发操作，不重复这些检查。

### 合并前：三个检查

**检查 1：工作区干净，且在 `main` 上。**

```bash
git status
git branch --show-current
```

工作区应当没有未提交的改动，当前分支应当是 `main`。如果目标分支也修改了你正在改的文件，`git merge` 会直接拒绝执行并提示 `Your local changes to the following files would be overwritten by merge`。这是 git 防止覆盖未提交内容的安全行为，不是仓库损坏；按提示先提交（或 `git stash`）那部分改动，再合并。

**检查 2：判断两个分支的关系。**

```bash
git merge-base main 'build/重构代码'                          # 共同祖先
git rev-list --left-right --count main...'build/重构代码'      # 左=main 独有，右=开发分支独有
git log --oneline 'build/重构代码' ^main                      # 待合入的提交列表
```

`--no-ff` 在两种情况下行为不同，先看清关系比事后判断更稳：

- 结果形如 `0 5`（`main` 左侧为 0）：`main` 只是落后于开发分支。普通合并会快进，只有显式 `--no-ff` 才会生成合并提交。
- 结果形如 `1 5`（两侧都非 0）：两个分支已经分叉。普通合并也会生成合并提交，但本文仍统一显式使用 `--no-ff`，避免依赖默认行为。

**检查 3（推荐）：记下合并前的 `main` 位置。**

```bash
git rev-parse main
```

把输出的完整哈希抄到本次合并的笔记里（也可以写进任务单，或写进本次合并提交的信息里）。合并一旦出问题，这个哈希就是恢复的锚点。

**不要为此打标签**（比如 `backup/before-merge-main-<时间戳>`）。本文的流程不需要标签：标签会长期留在本地仓库的引用列表里，容易和真正的版本标签混淆，事后还要记得清理。记一个哈希就够了。

作为兜底，git 在合并时会把合并前的 `HEAD` 记进 `ORIG_HEAD`，可以用它对照：

```bash
git rev-parse ORIG_HEAD
```

但 `ORIG_HEAD` 只有一格：之后任何一次 `merge`、`rebase`、`reset`、`pull` 都会覆盖它，所以它只在「刚合并完、还没做别的操作」这一小段时间内可靠。真正稳的还是检查 3 记下的那个哈希。

做完检查 3 之后，到合并提交完成为止，不要在另一个窗口里再对仓库做提交、切换分支或 Pull。原因：`main` 的基点可能在这段时间里变化。例如有人在这期间提交并推送了改动，你检查 3 记下的哈希就会过时，「本地领先 N 个提交」这类判断也可能不准。如果中途状态确实变了，重新执行检查 1 和检查 2，再继续合并。

### 合并后：两个验证

**验证 1：确认合并节点存在且有两个父提交。**

```bash
git log --graph --oneline --decorate -15
git show -s --format='%h %p %s' HEAD
git log --first-parent --oneline main
```

紧接合并后的 `HEAD` 应当显示两个父提交哈希。

**验证 2：确认改动已完整合入。**

```bash
git diff --stat 'build/重构代码' HEAD    # 相比开发分支多出来的内容
git log --oneline origin/main..main      # 真正会被推送的本地提交
```

如果期望是「开发分支的代码全部进入主分支」，那么第一条命令的输出里，应当只列出那些确实只在 `main` 上存在的提交（例如为本次合并写的说明文档）所带来的改动；如果它列出了本该来自开发分支的代码差异，说明合并结果不完整，需要检查。

## 在 CLion 中操作

以下以将 `build/重构代码` 合入 `main` 为例。不同 CLion 版本的菜单文字和选项位置可能不同。

1. **提交开发分支上的改动。** 在 Commit 窗口确认需要合入的代码已经提交，工作区没有待处理的改动。
2. **切换到 `main`。** 点击分支菜单，选择 `main` →“签出 / Checkout”。
3. **同步主分支。** 如需同步远程，在 `main` 上执行 Pull。若出现分叉或冲突，先处理完再继续。
4. **做完合并前检查。** 按上一节的「合并前必做检查」确认工作区干净、确认两个分支的关系，并把合并前 `main` 的哈希记下来。这一步最容易漏，也最影响能不能收尾。
5. **打开合并对话框。** 从顶部菜单进入 **Git → 合并… / Merge…**，选择来源分支 `build/重构代码`。
6. **启用禁止快进。** 在选项区域或“修改选项 / Modify options”中找到并启用 **`--no-ff` / No fast forward**。保持 squash 关闭。
7. **填写提交信息。** 如果 IDE 弹出了合并提交信息的输入框，按本文下一节「合并提交的信息怎么写」填写；想保留 git 默认风格就留空。
8. **执行合并。** 没有冲突时，IDE 通常会直接创建合并提交；如果启用了不自动提交选项，则还需要手动提交。
9. **处理冲突。** 如有冲突，使用 IDE 的冲突解决窗口检查并解决每个文件，然后完成合并提交。提交时不要启用“修正上次提交 / Amend”。
10. **检查并推送。** 在 Git Log 中确认出现合并节点，完成上一节的「合并后验证」，运行项目所需验证后，再按「合并完成后推送」核对推送范围并推送 `main`。

分支快捷菜单中的“将 `build/重构代码` 合并到 `main` 中”可能直接执行默认合并。要保证生成合并提交，必须确认操作使用了 `--no-ff`。

如果当前版本找不到 `--no-ff` 选项，可以使用 CLion 内置 Terminal 执行下一节命令，再回到 Git Log 查看结果。

## 使用 CLion 内置终端操作

确认开发分支的改动已提交后，在项目根目录执行：

```bash
# 确认当前分支和工作区状态
git status

# 切换到主分支，并同步远程主分支
git switch main
git pull --ff-only origin main

# 按「合并前必做检查」判断分支关系，并记下合并前的 main 位置
git rev-list --left-right --count main...'build/重构代码'
git rev-parse main

# 保留开发历史，并创建明确的合并提交
git merge --no-ff 'build/重构代码' -m "Merge branch 'build/重构代码'"
```

如果 `pull --ff-only` 提示无法快进，应先检查本地与远程的分叉原因，处理后再执行合并。

如果合并出现冲突，解决后将冲突文件标记为已解决，再完成提交：

```bash
git add <已解决的文件路径>
git merge --continue
```

如果决定取消尚未完成的合并，可执行 `git merge --abort`。

合并完成后按「合并后验证」检查历史和合并提交的父提交。紧接合并后的 `HEAD` 应显示两个父提交哈希。

## 合并提交的信息怎么写

`-m` 是必须的。git 在为合并创建提交信息时默认会拉起编辑器；在非交互环境（脚本里、编辑器未配置好的 CLion Terminal、CI）下，这一步会卡住而等不到输入。`GIT_MERGE_AUTOEDIT=no` 可以让 git 在这种场景下不打开编辑器，改用默认文案。

`-m` 的内容可以按需选择：

```bash
# 保留 git 默认风格，Git Log 里能直接看出合的是哪个分支
git merge --no-ff 'build/重构代码' -m "Merge branch 'build/重构代码'"

# 按项目的提交信息习惯写
git merge --no-ff 'build/重构代码' -m "feat: 重构代码完成仿真测试"
```

如果只写 `-m "feat: 重构代码完成仿真测试"`，Git Log 里就看不出这次合并的来源分支。想两者兼顾，可以给两个 `-m`：第一个成为标题，第二个成为正文。

```bash
git merge --no-ff 'build/重构代码' \
  -m "feat: 重构代码完成仿真测试" \
  -m "Merge branch 'build/重构代码'"
```

在 CLion 里填写合并提交信息时同理：提交信息输入框留空会走 git 默认文案，填了就以你填的为准。

## 合并完成后推送

推送前先核对真正会被推送的内容：

```bash
# 只列出本地有、远程没有的提交
git log --oneline origin/main..main

# 预演一次推送（可选）
git push --dry-run origin main
```

注意区分两件事：`git status` 里显示的「领先几个提交」，和实际会不会被推送，并不是同一个判断；以 `origin/main..main` 的输出为准。

`git push --dry-run` 在 https 远端且本机没有配置凭据时会以 `could not read Username for 'https://github.com'` 之类的信息失败。这是凭据问题，不代表仓库有问题；本地提交本身不受影响。

确认无误后推送：

```bash
git push origin main
```

`git push origin main` 只推送这一个分支。本文的流程不建标签，所以不存在「备份标签被顺带推上去」的问题；同时也别用 `git push --tags`，那会把仓库里其他无关的标签一起推走。

推送后，`origin/main..main` 应当为空。确认合并无误后不需要额外清理。

## 如果已经误做了快进合并

再次执行 `git merge --no-ff` 不会补出合并节点，因为开发分支已经包含在 `main` 中。需要先恢复到合并前的位置，再重新合并。

只有在满足以下条件时，才使用下面的恢复步骤：

- 这次快进合并尚未推送到远程 `main`。
- 工作区干净，没有未提交的改动。
- 开发分支仍保留所有开发提交。
- 已确认合并前 `main` 的准确提交位置。

在 CLion 中：

1. 确认当前分支仍是 `main`。想留条退路的话，可以先在当前位置建一个临时分支（是分支不是标签，用完即删）：`git branch pre-merge-main-<时间戳>`。
2. 在 Git Log 中找到合并前的 `main` 提交，位置来自「合并前必做检查」的检查 3 记下的哈希；用 `git show -s --format='%h %s' <哈希>` 确认选对了提交。如果当时没记，可以查 `git reflog main`，或用 `git rev-parse ORIG_HEAD`（这两个都要求此后没做过别的 merge / rebase / reset / pull）。注意：中间的 reset、切换、重新合并等操作会把合并前那条 reflog 记录挤到更下面，容易看错行；`ORIG_HEAD` 又只有一格、会被后续操作覆盖——所以事前把哈希抄下来最可靠。如果远程主分支仍指向该位置，也可以选择带 `origin/main` 标记的那个提交。
3. 右键该提交，选择“将当前分支重置到此处… / Reset Current Branch to Here”。
4. 选择 **Hard（硬重置）**。这会同时恢复分支指针、暂存区和工作区，因此必须先满足上述条件。
5. 按前面的步骤，使用 `--no-ff` 重新合并开发分支。

例如，本项目的 `109472d` 是初始化提交；只有确认某次合并前的 `main` 确实在这里时，才能将它用作恢复目标，不要把这个哈希当作固定操作参数。

**Soft（软重置）后把改动重新提交一次，会得到汇总提交，无法生成本文要求的双父节点合并提交。**

如果快进结果已经推送到共享 `main`，不要直接重置并强制推送；这涉及重写共享历史，需要先与协作者约定处理方式。

## 三种合并方式的区别

| 方式 | 保留开发分支原提交 | 新建合并提交 | 常见结果 |
| --- | --- | --- | --- |
| 默认 `git merge` | 是 | 分叉时创建；可快进时不创建 | 图形取决于分支关系 |
| `git merge --no-ff` | 是 | 有待合入提交时创建 | 保留分支汇合节点，本文推荐 |
| `git merge --squash` 后提交 | 不通过这次操作引入原提交历史 | 不创建双父节点合并提交 | 主分支新增一个汇总提交 |

需要快速查看主分支每次集成的记录时，可执行 `git log --first-parent --oneline main`。它沿主分支一侧显示历史，保留完整开发提交的同时，也能方便地查看每次合并。
